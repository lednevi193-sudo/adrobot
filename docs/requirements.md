# Adrobot — функциональные требования

Источники: ТЗ в Notion («Adrobot ТЗ»), видео «keitaro wrapper - test», разведка API стенда `https://tlgk.host` (18.11.2026).

## 0. Глоссарий

| Термин | Значение |
|---|---|
| Кампания | Сущность Keitaro: ссылка трекера + домен, группа, источник, набор потоков |
| Поток (stream) | Правило внутри кампании. Потоки проверяются по `position`, сверху вниз |
| Оффер | Конечная страница. Привязка оффера к потоку имеет вес `share` (в процентах) |
| Обёртка | Наше приложение: своя БД поверх Keitaro API |
| Опубликовано | Состояние, которое сейчас лежит в Keitaro |
| Черновик | Изменения в обёртке, которые ещё не отправлены в Keitaro |

## 1. Создаватор кампаний

**FR-1.1. Форма.** Три поля и кнопка **Create**:
- **Name** — название кампании, обязательное, 1–100 символов;
- **Geo** — один или несколько ISO-кодов стран из двух латинских букв через запятую (`AU` или `MX,AU,RO`). Ввод приводится к верхнему регистру, пробелы и дубли убираются (Q1);
- **Offer** — поле с автодополнением (FR-1.2).

**FR-1.2. Поиск оффера.** Автодополнение запрашивает наш бэкенд, а тот — Keitaro (`GET /offers`). Поиск идёт по ID и по подстроке в названии без учёта регистра. Выводится не больше 20 вариантов в формате `[id] name`. В поиске участвуют только офферы в состоянии `active`.

**FR-1.3. Создание.** По нажатию **Create** в Keitaro создаётся кампания:
- `name` = префикс из конфигурации (`CAMPAIGN_PREFIX`, по образцу стенда `test_<фамилия>_`) + имя из формы (Q5);
- `type = position` (ротация потоков по позиции);
- домен, группа и источник берутся из конфигурации (`.env`). Значения по умолчанию для стенда:

  | | id | name |
  |---|---|---|
  | домен | 1813 | `kylovoa.com` |
  | группа | 10332 | `FORTESTS` |
  | источник | 836 | `FORTESTS` |

**FR-1.4. Поток 1 («Geo → Google»).**
- `position = 1`, `type = forced` (перехватывающий);
- фильтр `country`, `mode = accept`, `payload = [<коды из Geo>]`;
- действие: HTTP-редирект на `https://www.google.com`.

**FR-1.5. Поток 2 («Offers»).**
- `position = 2`, `type = regular`, без фильтров;
- выбранный оффер с весом `share = 100`.

**FR-1.6. Целостность.** Если кампания создалась, а один из потоков нет, созданная кампания удаляется (компенсирующее действие), и пользователь видит ошибку. Полусобранных кампаний в Keitaro оставаться не должно.

**FR-1.7. Результат.** После успешного создания:
- кампания и её потоки сохраняются в нашей БД;
- пользователь видит ID кампании, ссылку трекера (`<домен><alias>`) и переход в редактор этой кампании.

**FR-1.8. Ошибки.**
- Ошибки валидации показываются у полей и не доходят до Keitaro.
- Ошибки Keitaro (4xx/5xx, таймаут) выводятся понятным сообщением с текстом ответа Keitaro.

## 2. Редактор кампании

### 2.1. Загрузка

**FR-2.1. Выбор кампании.** Открыть можно любую кампанию Keitaro по ID. В списке по умолчанию показываются наши кампании (с префиксом `CAMPAIGN_PREFIX`), переключателем — все (Q2).

**FR-2.2. Fetch streams.** Кнопка забирает из Keitaro потоки кампании (`GET /campaigns/{id}/streams`) и сливает их с нашей БД:
- **Потоки без офферов** (`offers = []`) сохраняются и показываются только названием и позицией. Их фильтры и действия не разбираются и не отображаются.
- **Потоки с офферами** показывают список офферов: `[id] название`, вес в процентах, состояние и кнопки действий.

**FR-2.3. Правила синхронизации при Fetch** (для каждой привязки оффер ↔ поток):

| В Keitaro | В обёртке | Результат |
|---|---|---|
| есть | нет | создать привязку в состоянии `active` с весом из Keitaro |
| есть | `active`, вес не закреплён | обновить вес из Keitaro |
| есть | `active`, вес закреплён, в Keitaro другой | оставить закреплённый вес, поток жёлтый, рядом подсказка «в Keitaro сейчас N%» (FR-2.9a) |
| есть | `removed` | вернуть в `active`: оффер вернули прямо в Keitaro |
| нет | `active` | перевести в `removed`, вес 0%, оставить в архиве. Не удалять! |
| нет | `removed` | без изменений |

Поток, который исчез из Keitaro, помечается удалённым и не показывается.

**FR-2.3a. Fetch при черновике (Q3).** Если в кампании есть жёлтые потоки, перед Fetch пользователь видит подтверждение: черновики будут отброшены. После согласия для каждого жёлтого потока выполняется Cancel (FR-2.10), затем синхронизация по FR-2.3.

### 2.2. Состояния

**FR-2.4. Состояния привязки оффера:**

| Состояние | Смысл | Вид | Вес |
|---|---|---|---|
| `active` | опубликован и в Keitaro | обычный | считается |
| `pending_add` | добавлен или возвращён, но не опубликован | обычный, с пометкой «new» | считается |
| `pending_remove` | удалён, но не опубликован | серый | 0% |
| `removed` | удалён и опубликован (или удалён в Keitaro) | серый, в архиве | 0% |

**FR-2.5. Состояния потока.**
- **Жёлтый (dirty)** — есть хотя бы одно неопубликованное изменение: `pending_*` или изменённый вес.
- **Белый** — состояние обёртки совпадает с опубликованным.

### 2.3. Действия с офферами (все локальные: в Keitaro ничего не уходит до Push)

**FR-2.6. Add offer.**
- В поток добавляется оффер через то же автодополнение, что в FR-1.2.
- Создаётся привязка `pending_add`, веса пересчитываются (FR-2.11), поток становится жёлтым.
- Нельзя добавить оффер, который уже стоит в потоке как `active` или `pending_add`.
- Если оффер лежит в потоке как `removed`, предлагается **Bring back** (дубль не создаётся).

**FR-2.7. Remove.**
- `active` → `pending_remove`, вес 0%, оффер серый, веса пересчитываются, поток жёлтый.
- `pending_add` → привязка удаляется сразу: её никогда не было в Keitaro.
- Закрепление веса у удалённого оффера снимается, после Bring back он возвращается незакреплённым (Q8).

**FR-2.8. Bring back.** Доступно для `removed` и `pending_remove`:
- `removed` → `pending_add`;
- `pending_remove` → `active` (отмена удаления).

В обоих случаях веса пересчитываются.

**FR-2.9. Pin / Unpin веса.**
- Pin фиксирует текущий вес оффера: при следующих пересчётах закреплённый вес не меняется.
- Закреплённый вес можно отредактировать вручную. Ограничение: сумма закреплённых весов не больше 100.
- Pin — локальная настройка обёртки, в Keitaro она не передаётся.
- Изменение закреплённого веса считается черновиком: поток становится жёлтым.

**FR-2.9a. Закреплённый вес — сознательное решение пользователя (Q7).** Закрепление означает «этому офферу всегда N%» (защитить проверенный оффер, осторожно тестировать новый, выполнить договорённость с сетью). Поэтому закреплённый вес главнее веса в Keitaro: если после Fetch в Keitaro у закреплённого оффера другой вес (его поменяли вручную в админке Keitaro), обёртка его не перетирает. Поток становится жёлтым, у оффера показывается фактический вес в Keitaro. Пользователь решает: Push (вернуть закреплённый вес в Keitaro) или Unpin (принять вес из Keitaro).

**FR-2.10. Cancel.** Откатывает поток к опубликованному состоянию:
- привязки `pending_add` удаляются из БД. Сам оффер (справочник) остаётся, удаляется только привязка;
- `pending_remove` → `active`;
- возвращённые через Bring back (`removed` → `pending_add`) → снова `removed`;
- веса и закрепления восстанавливаются из последнего опубликованного снимка: закрепления, сделанные или изменённые после последнего Push, тоже отменяются (Q9);
- поток становится белым.

**FR-2.10a. Подтверждение Cancel.** Перед откатом пользователь видит список того, что будет отброшено, и подтверждает его. Пример: «Будет отменено: добавление оффера [25327] …; удаление оффера [17210] …; закрепление [18813] … на 50%». Список строится из разницы между текущим состоянием потока и опубликованным снимком. Тот же список показывается в подтверждении Fetch при черновике (FR-2.3a).

Частичная отмена (отказаться от одного изменения, сохранив остальные) делается не через Cancel, а точечно: Remove для добавленного оффера, Bring back для удалённого, Unpin или правка для закрепления.

### 2.4. Веса

**FR-2.11. Алгоритм пересчёта.** Запускается после каждого Add, Remove, Bring back и изменения закреплённого веса:
1. В расчёте участвуют привязки `active` и `pending_add`. У `pending_remove` и `removed` вес 0.
2. `P` = сумма закреплённых весов участников, `N` = число незакреплённых участников.
3. Остаток `100 − P` делится поровну на `N`.
4. **Веса только целые**, потому что Keitaro хранит `share` как integer. Каждый получает `⌊(100−P)/N⌋`, а остаток `(100−P) mod N` раздаётся по +1 первым незакреплённым в порядке позиции. Пример: 3 оффера → 34/33/33.
5. Сумма весов участников всегда ровно 100.

**FR-2.12. Граничные случаи.**
- Все участники закреплены и `P ≠ 100` → предупреждение у потока, Push блокируется.
- `P > 100` → нельзя сохранить закреплённый вес.
- В потоке не осталось участников (все удалены) → Push блокируется: поток с офферами не может стать пустым (Q4).

### 2.5. Публикация

**FR-2.13. Push.**
1. Отправляет в Keitaro итоговый список офферов потока: участники с их `share`.
2. После успеха:
   - `pending_add` → `active`;
   - `pending_remove` → `removed`;
   - текущие веса сохраняются как опубликованный снимок;
   - поток становится белым.
3. После Push повторно читаем поток из Keitaro и сверяем, что опубликовалось то, что отправили.

**FR-2.14. Ошибка Push.** Черновик остаётся без изменений, поток остаётся жёлтым, пользователь видит ошибку Keitaro.

**FR-2.15. Пересчитанные веса после Push.** После повторного Fetch закреплённый вес остаётся тем, что задал пользователь. Остальные веса совпадают с опубликованными.

## 3. Нефункциональные требования

- **NFR-1. Стек:**
  - FastAPI + SQLAlchemy 2.x (синхронный);
  - PostgreSQL в Docker, драйвер psycopg 3;
  - httpx для Keitaro;
  - фронтенд: Vue 3 + TypeScript + Naive UI, сборка Vite. В разработке Vite проксирует `/api` на FastAPI, собранная статика раздаётся тем же FastAPI.
- **NFR-2. Конфигурация через `.env`:** `KEITARO_URL`, `KEITARO_API_KEY`, `DATABASE_URL`, ID домена, группы и источника. Секреты в git не попадают.
- **NFR-3. Keitaro-клиент:**
  - заголовки `Api-Key` и явный `User-Agent` (без него Cloudflare отвечает 403);
  - таймауты;
  - ошибки Keitaro превращаются в понятные сообщения.
- **NFR-4. Общий стенд.** На стенде работают и другие кандидаты. При разработке и проверке изменяем только свои кампании — с префиксом `CAMPAIGN_PREFIX`.
- **NFR-5. Запуск.** `docker-compose.yml` для Postgres, README с инструкцией по запуску.
- **NFR-6. Тесты.** Unit-тесты на алгоритм весов (FR-2.11/2.12) и правила синхронизации (FR-2.3).

| # | Вопрос | Решение | Статус |
|---|---|---|---|
| Q1 | Geo — одна страна или несколько (в макете `MX,AU,RO,...`)? | Список через запятую. Фильтр Keitaro и так принимает массив | принято |
| Q2 | Редактор работает с любыми кампаниями Keitaro или только с созданными нами? | С любыми по ID, в списке по умолчанию наши | принято |
| Q3 | Что делает Fetch, если в потоке есть неопубликованный черновик? | Подтверждение, затем Cancel черновика и синхронизация | принято |
| Q4 | Можно ли удалить из потока последний оффер? | Push пустого потока запрещён | принято |
| Q5 | Какой префикс у названий наших кампаний? | `CAMPAIGN_PREFIX` в `.env`, по образцу стенда `test_<фамилия>_` | принято |
| Q6 | Ключу доступен только оффер 18813. В потоках других кандидатов есть 25327, 17210 и 24800, но `GET /offers/{id}` по ним отвечает 403 — похоже на ограничение прав пользователя ключа. Создать оффер (`POST /offers`) или группу офферов (`POST /groups`) тоже нельзя: 403 «You have no permission» | Попросить заказчика открыть ещё 2–3 оффера или выдать права на создание офферов. | Q7 | Вес закреплённого оффера изменили вручную в Keitaro. Что после Fetch? | Побеждает обёртка: закрепление — сознательное решение пользователя (FR-2.9a) | принято |
